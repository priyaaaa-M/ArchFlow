## COMPONENT EXTRACTION RULES

### Components
- Include ONLY production runtime components that handle actual traffic/data
- Normalize names to **Title Case** (e.g., "api gateway" → "API Gateway")
- Use **descriptive but concise** names (2-4 words max)
- Infer obvious missing components:
  - If services mentioned but no gateway → add API Gateway
  - If database mentioned but no cache → consider adding cache layer
  - If async processing mentioned but no queue → add message queue
- **Assign appropriate component types** based on actual role

### Component Types (use EXACTLY these)
- `client`: User-facing applications (Mobile App, Web Browser, Desktop Client)
- `gateway`: Entry points (API Gateway, Load Balancer, Reverse Proxy)
- `service`: Business logic services (User Service, Order Service)
- `core_service`: Critical business services (Authentication Service, Payment Service)
- `database`: Data stores (PostgreSQL, MongoDB, Cassandra, DynamoDB)
- `cache`: Caching layers (Redis, Memcached)
- `queue`: Message queues (Kafka, RabbitMQ, SQS, AWS SQS)
- `streaming`: Stream processing (Kafka Streams, Apache Flink)
- `external_service`: Third-party integrations (Payment Gateway, Email Service, SMS Provider)
- `edge`: CDN or edge computing (CloudFront, Cloudflare)
- `infra`: Infrastructure (Kubernetes, Docker, Monitoring Stack)

## RELATIONSHIP RULES (ByteByteGo Style)

### Relationship Labels MUST Be Descriptive and Action-Oriented
Use **verb phrases** that clearly describe the interaction:

**Good Examples:**
- "Authenticates user"
- "Publishes order events"
- "Queries product catalog"
- "Stores user data"
- "Caches session data"
- "Streams video content"
- "Sends email notification"

**Bad Examples:**
- "uses" (too vague)
- "connects to" (no semantic meaning)
- "talks to" (unprofessional)
- "data" (what kind of data?)

### Relationship Pattern Detection
Your labels should help identify these patterns:

**Synchronous (Solid Lines):**
- "Calls API", "Sends HTTP request", "Invokes gRPC", "Requests data"

**Asynchronous (Dashed Lines):**
- "Publishes event", "Sends message", "Queues task", "Notifies", "Emits event"

**Read Operations (Dotted Lines):**
- "Queries", "Fetches", "Reads", "Retrieves", "Searches"

**Write Operations (Solid Red):**
- "Stores", "Writes", "Updates", "Persists", "Saves"

**Data Flow (Bold Lines):**
- "Streams data", "Replicates", "Syncs", "Transfers", "ETL process"

### Relationship Direction
- Always specify **source → target** based on data/control flow
- Source initiates the interaction
- Target responds or receives
